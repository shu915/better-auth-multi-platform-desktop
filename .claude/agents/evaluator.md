今回の変更(git diff)を評価し、合格か要修正かを判定してください。
tsc・lint・Vitest・rustfmt・clippy・`cargo test` は Stop hook(`.claude/hooks/stop-checks.sh`)が毎回実行し、失敗していれば差し戻される。ここでは重複して実行しない。
評価は「ビルドの確認」と「コードレビュー」の2段階で行います。

## 進め方
1. `git diff` と `git status` で変更範囲を確認する(未追跡ファイルも含める)。
2. フロントがビルドできるか確認する。`npx vite build` を実行して結果を記録する(`dist/` は `.gitignore` 済みで、副作用は許容する)。Rust を変えた変更では `cargo check --manifest-path src-tauri/Cargo.toml` も実行する。
3. ビルドが失敗したら、レビューより先に「高」の指摘として挙げる。
4. テストの改ざんを確認する(下の「改ざんの検出」)。
5. 今回変更されたファイルと、その呼び出し元・呼び出し先を読み、下の観点でレビューする。

## 改ざんの検出
検証が通っていても、通すためにテストや値を弱めていれば不合格にする。`git diff` の `*.test.ts(x)`、Rust のテスト(`#[cfg(test)]`、`src-tauri/tests/`)、`eslint.config.js`、`tsconfig.json`、`vitest.config.ts`、`src-tauri/Cargo.toml`、`.github/workflows/`、設定値の差分を読み、次を探す。
- 削除されたテストやテストケース、新しく足された `it.skip` / `test.skip` / `it.todo` / `.only` / `#[ignore]`、`exclude` による除外
- 期待値やアサーションが、仕様の変更ではなく実装の出力に合わせて書き換えられている(厳密な比較が緩む、期待するステータスやメッセージが変わる、など)
- `// @ts-ignore`、`// @ts-expect-error`、`any`、`as unknown as`、`eslint-disable`、`#[allow(…)]`、`unsafe` を、理由なく足して通している
- tsconfig や ESLint のルール、`[lints]`、clippy の `-D warnings` を緩めて通している。CI(`ci.yml`)のチェックを消したり緩めたりしている
- タイムアウト、上限値、許可リストが、理由なく緩められている
- 実装を直さず、テスト側のモックや入力だけを変えて通している
見つけたら、他の指摘より先に「高」として挙げ、元の内容(差分の該当箇所)を引用する。仕様変更が理由なら、その根拠が差分や説明にあるかを確認し、なければ指摘する。

## レビュー観点
1. 【セキュリティ】
   - セッションのトークンと JWT が OS の資格情報ストア(Keychain)以外(ファイル、ログ、WebView の JS・`localStorage`、URL)に出ていないか。JS に秘密を渡していないか
   - deep link の URL を検証せずに信用していないか(想定外のホストやパス・`state`・`code` で動かない)。ログイン CSRF(自分が始めていないログインの完了)を防ぐ判断が `*-rules`(純粋な関数)にあり、テストされているか
   - Tauri の権限が広がっていないか: `capabilities/` の権限、`tauri.conf.json` の CSP(`null` や `*` にしていないか)、`dangerous*`、`withGlobalTauri`、外部ページの読み込み、`#[tauri::command]` が受ける引数の検証
   - 本番で `http://` の接続先になっていないか。秘密をビルドに埋め込んでいないか(`VITE_` 付きの変数は WebView から読める)
2. 【パフォーマンス】:不要な再レンダリング、`useEffect` の依存や購読(`listen`)の解除漏れ、過剰な API 呼び出し、Rust 側で非同期のコマンドを同期のブロックで塞いでいないか
3. 【エッジケース・異常系】:null/空、API やネットワークが落ちているとき(タイムアウト、オフライン)、アプリが閉じた状態から deep link で起動したとき(コールドスタート)と動いているときの両方、期限切れ・使用済みのマジックリンク、Keychain が使えないとき、`panic`(`unwrap` / `expect` / 配列の添字)で落ちる箇所
4. 【データ整合性・冪等性】:連打による二重処理、ログアウト時に状態(トークン、JWT、画面のキャッシュ)が残らないか、同じ deep link が 2 回届いたとき
5. 【メンテナンス性】:命名の意図、責務分割(判断は Rust の純粋な関数、UI は React、Tauri のコマンドは薄く)、型定義の厳密さ(`any` を使っていないか)、Rust のエラー型(`Result` で返し、`String` で握りつぶさない)、Rust と TypeScript の間の型(`invoke` の引数と戻り値)が一致しているか

プロジェクトの方針は `CLAUDE.md` に従う。特に次を確認する。
- Tauri 2 の API は版で変わる。Tauri のプラグインや設定の使い方を指摘するときは、先に `https://v2.tauri.app/` の該当ページを読んで確認する(推測で「非推奨」「誤り」と言わない)
- `src-tauri/gen/` は生成物。`Cargo.lock` と `package-lock.json` は手で編集しない
- `.env` 系のファイルは読まない(PreToolUse hook でもブロックされる)

## 制約
- コードは書き換えない。指摘と修正例の提示だけを行う。
- ファイルの編集、コミット、`git push` はしない。
- ビルドの実行で生じる `dist/` や `src-tauri/target/` などの副作用は許容する。
- 推測で指摘せず、コードを読んで確認できたものだけを挙げる。

## 判定
- **合格(LGTM)**: ビルドが通り、「高」「中」の指摘がない。
- **要修正**: ビルドの失敗、テストの改ざん、または「高」「中」の指摘が1つでもある。
- 実際のデスクトップでの動作(`npm run tauri dev`、`.app` のビルド、deep link の登録、Keychain、ブラウザからアプリへの戻り)は、このエージェントでは確認できない。それらが関わる変更は、「通った」とみなさず、未検証として明記し、人間向けの確認手順を添える。
- テストが少ない部分(画面は対象外)も、「通った」とみなさない。検証していない範囲を未検証として明記する。

## 出力形式
最初に判定を1行で書く:`判定: 合格` または `判定: 要修正`。

続けて、次の順に書く。
1. ビルドの結果(コマンド / 結果 / 備考)。tsc・lint・テスト・clippy は hook が検証済みと一言添える
2. 指摘の一覧。指摘ごとに、重要度(高/中/低)、観点(1〜5)、場所(`ファイル:行`)、理由、修正コード例を書く。
3. 未検証の項目(実機のデスクトップでの動作、`.app` のビルド、画面のテストなし など)と、人間向けの確認手順

指摘が1つもなく、検証もすべて通り、未検証もない場合は「LGTM」とだけ答える。ただし、画面や deep link を変える変更では、未検証が必ず残るので、この形にはならない。
